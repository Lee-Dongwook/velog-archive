### Intro

```yaml
name: Next.js Deployment

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v3

      - uses: pnpm/action-setup@v2
        with:
          version: 8

      - uses: actions/setup-node@v3
        with:
          node-version: 20

      - name: Install Pnpm Package
        run: pnpm install
        working-directory: ./profile

      - name: Build Next.js App
        run: pnpm build
        working-directory: ./profile
```

다음 yaml 파일은 Github Action의 workflow 예시입니다. 해당 프로젝트는 변경 사항이 많을 것으로 예상되어 애플리케이션의 빌드 과정을 자동화할 수 있도록 구성해봤습니다.

<hr />

### 🔎CI/CD

CI/CD라는 용어는 과연 무슨 뜻일까요?

CI/CD는 Continuous Integration / Continuous Delivery의 약자로
지속적인 통합, 지속적인 서비스 제공, 지속적인 배포의 개념을 의미합니다.

애플리케이션의 개발 단계를 자동화하여 사용자들에게 더 빠르게 전달할 수 있는 환경을 구축합니다.

<hr />

### Github Action

![](https://velog.velcdn.com/images/dlehddnr99/post/b9f2023b-af47-4203-8d94-f1350342e6fe/image.png)

`Github Action은 CI/CD 자동화 플랫폼`으로 특정 Repository에 대해서 애플리케이션을 빌드하거나, 빌드된 애플리케이션을 배포하는 등의 작업들을 자동화 해줍니다.

![](https://velog.velcdn.com/images/dlehddnr99/post/ba5fbc89-27a0-4489-8292-1f1804579c6b/image.png)

Github Action의 workflow는 특정 event가 발생 시, 하나 이상의 job을 수행하게 됩니다. 작업들은 순차적 혹은 병렬적으로 실행되며, 각각의 작업은 runner라고 불리는 가상머신이나 container 내부에서 수행됩니다.

<hr />

### Github Action 구성 요소

Github Action의 구성 요소들을 알아보겠습니다.

- Workflows
- Events
- Jobs
- Actions
- Runners

다음과 같이 크게 5가지로 정리 할 수 있습니다.

#### Workflow

특정 레포지토리에서 발생한 이벤트에 대응하여 자동으로 실행되는 프로세스를 `workflow` 라고 부릅니다.

#### Event

워크플로우가 실행되기 위한 조건을 `event`라고 부릅니다. 주로 main 브랜치에 push되었을 때나 pull request가 머지된 경우와 같은 상황을 이벤트로 설정합니다.

#### Job

workflow를 이루는 개별 작업 단위로, 빌드, 테스트, 배포 등 다양한 목적으로 사용되며 독립적으로 실행됩니다.

#### Action

재사용 가능한 단일 작업의 단위를 `action`이라고 합니다. 다른 프로젝트에서 만들어진 action을 가져와 사용하거나, 직접 action을 정의할 수 있습니다.

#### Runner

workflow에 정의된 각 job을 실행하는 agent를 `runner`라고 합니다.

### Conclusion

애플리케이션의 규모가 커짐에 따라 CI/CD 환경 구축이 더욱 중요해지고 있습니다. 소스 코드의 통합과정을 자동화하고, 코드 병합 시의 충돌을 미연에 방지하여 애플리케이션 개발의 신속성과 정확성을 확보합니다.
